# ADR-0013: 任务模式与产物分类（评分是可选模式，不是核心概念）

- 状态：已接受
- 日期：2026-09-09（本版取代原「产物泛化——漏洞不是唯一产出」，那一版把一次评测需求写成了产品一等公民）

## 背景

Sharp 曾被用于一次授权评测（腾讯 TSec Benchmark，a-01~a-18 的 CTF 式靶场）。那类任务的产物是**旗帜与分值**，不是安全漏洞。为此给产物表加了 `kind`（`vuln` / `flag` / `finding`）与 `score`，界面上做了记分板与旗帜徽章。

问题在于**它被当成了工具的一等公民**：架构文档把它写成差异化能力，渗透项目的界面也挂着"得分""旗帜"这类与授权测试无关的概念——使用者会误以为 Sharp 是个 CTF 竞赛工具，而工具自身的主线（证据可审计、审批边界、资产积累）反而被稀释。

这里必须区分两件被混在一起的事：

| 能力 | 范围 | 判断 |
| --- | --- | --- |
| **产物分类** `kind = vuln \| finding` | 授权渗透中真实存在："不是漏洞但值得记录的发现"（配置缺陷、信息泄露线索、可疑入口） | **通用价值，保留** |
| **记分** `flag` + `score` + 记分板 | 只对评测 / CTF 有意义 | **场景特化，收敛为可选模式** |

## 决策

把评分收敛为**项目级任务模式**（`projects.task_mode`），而不是全局概念：

| `task_mode` | 定位 | 产物语义 | 界面 | 注入的提示词 |
| --- | --- | --- | --- | --- |
| `pentest`（**默认**） | 授权渗透 | 只谈安全发现（`vuln` / `finding`） | 无记分板、无旗帜筛选项 | 明确要求**不要**输出 `kind` / `score` |
| `scored` | 评测 / CTF | 额外支持 `flag` + `score` | 记分板、旗帜徽章、旗帜筛选 | 注入 flag 输出规范 |

配套规则：

1. **默认必须是渗透模式**。绝大多数项目不是评测；新项目一律 `pentest`，除非显式指定。
2. **模式决定提示词，而不是留给模型猜**。`explore.md` / `bootstrap.md` 用 `{scoring_note}` 占位符，dispatcher 按项目模式注入：渗透模式给"禁止输出 `kind`/`score`"，评测模式给 flag 规范。漏注入会让 worker 读到字面占位符，因此有回归测试（`tests/test_task_mode.py`）。
3. **模式可切换**：`PUT /projects/{id}/task-mode`。真实流程里存在"先按渗透测，后来决定拿去跑分"的情况，不该逼人重建项目。
4. **历史数据保留原语义，不迁移**：`proj_004` 的 11 条 `flag` 记录仍是旗帜，只是仅在该项目（`scored`）下呈现。
5. **回退不需要动数据库结构**：去掉 `score` 列与记分板不影响渗透路径（`kind` 默认 `vuln`），这正是"可选模式"相比"一等公民"的好处。

## 备选方案

- **把记分做成一等公民**（原方案）：实现最省，但产品叙事被单一场景绑架——渗透用户会看到无意义的"得分"，而文档会把特化能力吹成差异化护城河。
- **彻底移除评分能力**：叙事最干净，但评测场景（TSec / XBOW 类）确实会出现，下次还要重写一遍；且移除 `score` 列涉及迁移与历史数据处置，收益不成比例。
- **分叉出"评测版"**：评测所需的图、审批、资产、报告能力与渗透完全重叠，维护成本翻倍。

## 后果

- 优点：**渗透主线保持干净**——界面与提示词里都不出现分数概念；工具定位不再被单次评测绑架。
- 优点：评测能力以配置形式保留，未来跑 XBOW / TSec 类基准时切换模式即可，不必重新开发。
- 优点：提示词按模式注入，模型不会在渗透任务里"发明"评分语义（此前那段 flag 指引是写死在提示词里的，任何项目都会读到）。
- 缺点：多了一个需要理解的项目维度；两条模式各自的提示词分支需要单独测试。
- 缺点：历史评测数据在渗透模式下不可见（有意如此，但必须在文档里说明，避免误以为数据丢了）。
