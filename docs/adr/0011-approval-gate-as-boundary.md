# ADR-0011: 审批闸门是产品边界，不是权限装饰

- 状态：已接受
- 日期：2026-09-09

## 背景

自动化渗透工具的核心风险不是"跑不动"，而是"跑太顺"：一个自主 agent 在授权范围内顺手做了破坏性操作（删数据、改配置、横向提权、批量利用），影响面从"验证漏洞"变成"事故"。工程上必须回答两个问题：

1. 高风险动作在**执行前**能不能被人拦一次？
2. 拦下来的东西，事后能不能说清"谁批的、什么时候批的、依据是什么"？

如果只在提示词里写"不要做危险操作"，等于把边界交给模型自觉——这不是工程边界。

## 决策

在高危行动的执行路径上设置**强制闸门**（gate），默认拦截、人工放行：

1. **拦截点在图写入路径上**：agent 判定为高危的行动（严重度 critical/high 或命中危险动作关键词）提交后进入 `pending`，**不可被认领**（claim 返回 403）。因为 dispatcher 是唯一写入方（ADR-0001/0003），闸门天然只有一处，不存在"绕过 API 直连"的路径。
2. **审批是显式记录**：`approval_events` 表 append-only 记录 decision（approved/rejected）、审批人、理由、时间；审批必须带项目上下文（`project_id`），不接受全局模糊审批。
3. **项目级急模式（emergency）**：真实对抗场景（时间窗、靶场评测）需要连续动作，允许整项目旁路闸门，但必须：仅 JWT 鉴权可用、带过期时间、开启/关闭都写审计。旁路的是"人工确认"，不是"记录"。
4. **闸门与资产账本、附件导出、知识库写入同源**：一切会改变外部世界或产生对外影响的动作都走同一条可审计路径。

## 备选方案

- **提示词约束**（"不要做危险操作"）：零成本，但不可验证、不可审计；模型越强越容易"自作主张地完成目标"。
- **工具白名单 + 参数校验**：能挡住已知危险命令，但渗透动作的危险性高度依赖上下文（同样是 `POST /user`，改自己还是改别人天差地别），静态规则拦不住语义风险。
- **只在事后审计**：事故已经发生，审计只能追责不能止损。
- **全自动不放行（全拦）**：安全但失去自动化意义；急模式提供了受控的例外通道。

## 后果

- 优点：默认安全（拦截是默认行为）；责任链清晰（每个高危动作有决策记录）；急模式让"要快"和"要留痕"不冲突。
- 优点：闸门位于图写入路径而非 UI 层，绕过 UI 直接调 API 也无法执行未批准的高危行动。
- 缺点：需要人工在场或提前开急模式，长无人值守任务的节奏会被打断；急模式被滥用则闸门形同虚设（用审计与过期时间约束）。
- 缺点：严重度判定依赖 agent 自报 + 关键词启发，存在漏判可能；因此验收盘点（ADR-0014）会额外列出"未确认高危"作为人工兜底检查项。
