# ADR-0003: 证据—行动图作唯一协作媒介

- 状态：已接受
- 日期：2026-07-14
- 修订：2026-09-09（术语定稿为「证据 / 行动 / 线索」，见 `docs/GLOSSARY.md`）

## 背景

长周期授权渗透的难点不是"跑一个扫描器"，而是：**结论要可追溯、执行要可中断续跑、人工判断要能插进来**。常见的替代做法是把 agent 的对话历史当状态（context 里记着做过什么），这在单轮任务里够用，在几天的多目标任务里会崩：

- 对话历史随进程死亡而消失，重启即失忆；
- 结论散落在自然语言里，无法被程序化查询（"哪些资产还没测过？"答不出来）；
- 多 worker 并行时，谁做过什么无法对账，重复劳动与互相覆盖不可控。

## 决策

把一次授权渗透测试建模为一张**有向图**，作为所有角色共享的唯一媒介。图里只有三类节点：

| 节点 | 语义 | 谁写 |
| --- | --- | --- |
| **证据（Evidence）** | 已被确认的事实：目标、发现的接口、拿到的凭据、验证过的漏洞结论 | agent 经 dispatcher 提交 |
| **行动（Action）** | 待执行或已执行的一步探索：从某组证据出发，去验证一个猜想 | bootstrap 自动派生 / 规划器派生 / 人工添加 |
| **线索（Lead）** | 人工给出的方向性提示，不构成证据也不构成任务 | 人工 |

规则：

1. **起点与终点也是节点**：`origin`（目标与已知信息）与 `goal`（验收标准）是两张种子证据；一次行动把结论连回 `goal` 即视为达成目标（完成判定落在图上，不落在进程状态里）。
2. **行动必须先有来源证据**：它记录 `from`（依据哪些证据）与 `to`（产出哪些证据）。这既表达推理链，也让"这个结论凭什么得出"可审计。
3. **唯一写入方是调度器**：agent 不能直接写图，只能经 dispatcher 提交；这样每一条图变更都可被审批闸门拦一次（ADR-0006/0011）。
4. **图即记忆**：worker 的上下文由「与本次行动相关的子图」渲染而来；进程重启后从图恢复，不依赖对话历史。
5. **图是关系型存储而非图数据库**：`facts` / `intents` / `intent_sources` / `hints` 四张表 + 邻接查询，够用且便于事务（ADR-0002）。

> 术语对照：对外文档与 UI 使用**证据 / 行动 / 线索**；代码内部标识符（表名 `facts`/`intents`/`hints`、API 路径、模型类名）为兼容性保持不变，映射见 `docs/GLOSSARY.md`。

## 备选方案

- **对话历史即状态**：实现最快，但重启失忆、无法程序化盘点、多 worker 无法对账。适合单轮任务，不适合长周期。
- **图数据库（Neo4j 等）**：图查询更强，但引入额外服务与运维，且本项目查询模式固定（按项目取子图、按状态取待办），关系型 + 邻接表足够。
- **任务队列（Celery/RQ 式）**：只表达"待办列表"，丢失"结论凭什么得出"的推导链；验收盘点与资产覆盖统计都无从实现。
- **纯文件系统产物（报告 + 中间文件）**：便于人读，但缺并发控制、缺状态机、缺审计。

## 后果

- 优点：结论可溯源（每条证据都有来源行动）、可程序化盘点（未测接口、待审批、未验证结论都是查询）、可中断续跑（进程重启不丢状态）、天然支持人工介入（往图里插线索或行动）。
- 优点：调度策略（优先级、放弃、阶段划分、截止时间）全都能落在图上的字段里，而不必新增子系统（ADR-0014）。
- 缺点：agent 必须把结论"翻译"成结构化提交，比自由文本多一步；dispatcher 作为唯一写入方是可靠性关键路径（单线程，见 ADR-0001）。
- 缺点：图会随任务变长而膨胀，需要摘要化渲染（ADR-0009）与阶段划分（ADR-0014）来控制上下文成本。
