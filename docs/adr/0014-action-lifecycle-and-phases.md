# ADR-0014: 行动生命周期与阶段模型

- 状态：已接受
- 日期：2026-09-09

## 背景

图的原始语义是**探索性**的：有来源证据就派生行动，行动做完就产出证据，直到某个行动连回 `goal` 就算完成。但长周期任务暴露三个图语义覆盖不到的问题：

1. **方向会变**：开局判断错的路径应该被明确终结，而不是永远挂着待办（挂着就一直被调度，浪费预算，也让"还剩多少活"失真）。
2. **价值不均**：同一时刻可能有一个高危验证和一堆低价值枚举，"先做哪个"在纯 FIFO 下无法表达。
3. **时间有边界**：真实任务有窗口（授权期、平台截止），到期后继续派发新探索是浪费；需要的不是"立刻停"，而是"停止开拓、把手上的收尾"。
4. **完成判定太二值**：只有"到 goal"和"没到 goal"，缺少中间层——一次任务通常要经过侦察、凭据获取、验证、报告几个段落，段落之间有天然结算点。

这四件事如果都靠规划器在自然语言里"记得"，就会退化成提示词工程，不可查询、不可统计、重启即失效。

## 决策

在图上分两层引入生命周期控制，**全部落在字段与表上，都可查询、可审计**：

**第一层：行动级（`intents` 表）**

- `priority`（整数，默认 0）：调度权重，高者先派发；同优先级按创建时间（FIFO）。
- `abandoned_at` / `abandon_reason`：显式放弃。放弃的行动不参与认领、不参与"未完成数"统计，但**保留在图上**（证据链不断裂，事后能解释为什么放弃）。
- 规划器（reason）被授权在规划时输出 `abandon` / `prioritize` 动作，人工也可通过 API 直接操作。

**第二层：项目与阶段级**

- `projects.deadline_at`：时间预算。到期后调度器**不再派发新行动**，正在跑的行动允许收尾；到期事实以一次性提示注入规划器上下文，使其主动转入收敛（写报告、结算阶段）。
- `sub_goals` 表（阶段）：比行动粗、比目标细的中间层，状态 `pending / active / done / abandoned`，带 `concluded_at`。规划器可提议与结算（`sub_goals.add/update`），人工可在界面增删。完成判定仍以终态 `goal` 为准，**阶段不替代终态**，而是把长过程切成可结算的小段。
- 完成前**验收盘点**把未结算阶段计入"仍有开放工作"，避免"最后一个行动一到 goal 就宣布完工，实际一堆阶段没收尾"。

**调度规则汇总**：待办 = 未放弃 ∧ 未认领 ∧ 审批放行；排序 = 优先级降序 → 创建时间升序；项目已过截止时间则不再新增派发。规则只有这一处（dispatcher 的派发决策），不散落在各调用点。

## 备选方案

- **只靠提示词管理节奏**（让规划器"自己记得别做无用功"）：不可查询、不可统计、重启失效，也无法给人一个"当前还剩多少活"的数字。
- **把放弃实现为删除**：图会断裂，事后无法解释某条证据为何缺失，违背可追溯原则（ADR-0003）。
- **多目标/多 Goal 替代阶段**：会破坏"唯一终态"的完成判定，让验收与完成语义变得含混；阶段是并列的进度概念，不是并列的终点。
- **到截止时间硬杀所有 worker**：粗暴且可能丢掉进行中的有效结论；当前策略是"停止开拓 + 提示收敛"，更贵但更稳。

## 后果

- 优点：方向调整、优先级、时间预算三类决策全部可查询、可审计、可回放；"还剩多少活"是查询而不是估计。
- 优点：阶段给了 agent 与人工共同的里程碑语言，长任务不再是黑盒。
- 缺点：`priority` 与阶段的自主使用依赖规划器判断力，可能出现"乱放弃"或"阶段刷屏"；currently 依靠提示词引导 + 人工可随时纠正（阶段可删改、行动可恢复优先级）。
- 缺点：字段与状态机增多，测试面扩大（每个状态转换都需要覆盖）；语义上要持续强调"阶段 ≠ 终态"以免误用为完成依据。
