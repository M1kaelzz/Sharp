# 交付质量、工作记忆与假设驱动

> 决策依据见 `docs/adr/0015-delivery-and-hypotheses.md`（修订版）。
>
> 本文取代同日"管理面三层"（资源账本 / 产出经济学 / 计划链）初稿——那一版是按**评测场景的效率指标**
> 推导的，方向已被否决。本版按**授权渗透的真实目标**（不遗漏、打得深、说得清、可复用）重排。

---

## 0. 校准原则

| 场景 | 目标函数 | 该优化什么 |
| --- | --- | --- |
| 评测 / 靶场 | 一定时间内拿最多分 | 广度、抢分、快速换题 |
| **授权渗透（Sharp 的定位）** | **不遗漏、打得深、说得清、可复用** | 证据质量、深度推进、交付物、跨任务积累 |

由此得出的红线（详见 ADR-0015"修订说明"）：

- ❌ 不按产出**强制排序**（目标不能换，排序最多作为建议）
- ❌ 不做**自动回收 / 自动止损**（判断权属于人，与 ADR-0011 一致）
- ❌ 不硬编码外部并发上限（资源约束只做"可见"，不做"抢占"）
- ✅ 可以：**沉淀已确认的前提**（省时间）、**暴露证据不足**（保交付）、**让假设驱动推进**（保深度）

## 1. 结论的可交付性（P0-1 · **已实现**）

### 1.1 机制

`server/finding_quality.py` 的 `assess_finding()` 计算"可复现四件套"的完备度：

| 项 | 字段 | 判定要点 |
| --- | --- | --- |
| 原始请求/响应 | `evidence` | 长度下限 + 不把"见截图"这类占位符算作证据 |
| 复现步骤 | `reproduction` | 长度下限 |
| 影响说明 | `impact` | 长度下限 |
| 定位 | `url` | 非空 |

- 结果作为**派生字段** `Vulnerability.quality` 随响应返回（`applicable/score/total/complete/missing/missing_labels/notes`），**不入库**、无迁移。
- `kind=flag` 等评分类产物 `applicable=false`（不参与评估）。
- `notes` 给**有指导性**的补充建议：证据含请求但无响应 → 提示补响应；反之提示补请求。

### 1.2 落点

- **报告**：`build_engineered_report_context` 为每条 finding 带 `evidence_quality`，并新增规则 `evidence_completeness_rule`——不完备结论必须写成「⚠️ 证据不足（缺 X）待补充」归入待补充类；另给 `finding_quality_summary`（共 N 条、M 条不足）。
- **界面**：漏洞列表「⚠ 证据不足」徽章（tooltip 列缺项）、漏洞库顶部统计、详情弹窗缺项与建议。
- **测试**：`tests/test_finding_quality.py`（16 例）。

## 2. 环境基线（P0-2 · **已实现**）

### 2.1 前提 ≠ 结论

| | 表 | 语义 | 生命周期 |
| --- | --- | --- | --- |
| 结论 | `facts` | 测试得到的结果 | 每轮新增；参与证据链与审计 |
| **前提** | `env_baseline` | 连通性、凭据有效性、可达性、工具可用性、目录布局 | **确认一次，长期复用** |

动机：实测同一条网络预检被重复执行 **144 次**——每轮独立会话从零构建上下文，"已确认的前提"被反复支付。

### 2.2 机制

- 表：`env_baseline(project_id, key, value, note, source, updated_at)`，主键 `(project_id, key)`
- API：`GET|PUT /projects/{id}/baseline`（批量 upsert，校验 key 非空/长度、value 长度、条目上限）、`DELETE /projects/{id}/baseline/{key}`
- 注入：`explore.md` / `bootstrap.md` 的 `{env_baseline}` 占位符由 dispatcher 渲染填充
- **空基线时提示词会给出创建基线的 API 调用形式**——否则机制会空转（worker 不知道要写）
- 规则：**信任基线**（已确认的前提不再重复验证）→ **扩展基线**（新确认的环境事实写入）→ 环境事实不进 `fact.description`
- 测试：`tests/test_env_baseline.py`（14 例）

## 3. 未验证假设（P0-3 · 设计中）

### 3.1 问题

真实渗透推进的本来逻辑是**假设驱动**：观察到一个现象 → 形成可证伪的猜想 → 设计一个动作去验证 → 得到新证据 → 产生新猜想。而当前 Sharp 只有"结论（facts）"与"待办（intents）"两类，**猜想无处安放**——它只能塞进意图描述的文字里，于是：

- 规划器每轮要重新读长文本才能"猜出"当前在追什么；
- 一条线索被验证/被否定之后，**没有结构化的结算**（否定的结论甚至不会留下痕迹）；
- 深度推进缺乏抓手：无法回答"这条线上还有哪些未验证的假设"。

### 3.2 模型

```sql
hypotheses(
  id TEXT, project_id TEXT,
  statement TEXT NOT NULL,          -- 可证伪的命题（"若...则..."），不是"这里有漏洞"
  status TEXT NOT NULL DEFAULT 'open',  -- open | testing | confirmed | refuted
  premise_fact_ids TEXT DEFAULT '',  -- 依据哪些证据提出（逗号分隔的 fact id）
  result_fact_id TEXT,               -- 结算时引用的证据
  created_by TEXT DEFAULT 'reason',  -- reason | human
  note TEXT DEFAULT '',              -- 结算说明（尤其 refuted：试过什么）
  created_at TEXT, concluded_at TEXT
)
-- 行动挂载：这一步是为了验证哪个假设（向后兼容，可空）
ALTER TABLE intents ADD COLUMN hypothesis_id TEXT;
```

**状态语义**：

| 状态 | 含义 | 谁能置 |
| --- | --- | --- |
| `open` | 已提出，尚未验证 | reason / 人工 |
| `testing` | 正在验证（有行动挂着） | reason / 人工 |
| `confirmed` | 验证成立（必须有 `result_fact_id`） | reason / 人工 |
| `refuted` | 验证不成立（必须写清试过什么） | reason / 人工 |

### 3.3 接口

| 端点 | 说明 |
| --- | --- |
| `GET /projects/{id}/hypotheses` | 列表（按状态与时间） |
| `POST /projects/{id}/hypotheses` | 创建（`hypothesis_id` 每项目自增 `h001…`） |
| `PATCH /projects/{id}/hypotheses/{hid}` | 状态流转 + 结算说明 + 结果证据 |
| SSE | `hypothesis_created` / `hypothesis_updated` |

### 3.4 规划器职责变化

提示词注入 `{hypotheses}`（open/testing 列表 + 依据证据 + 已试次数），并授权输出：

- `hypotheses.add`：从当前证据派生新假设（**要求可证伪**）
- `hypotheses.update`：把验证结果结算到假设上

规划策略从"找线索"改为"**消灭未验证假设**"：优先派发**信息增益最大**的前提是"一次行动能证实或证伪"的假设（而非"看起来重要"的目标）——这条规则同时天然服务于深度（沿着链条往下推）。

### 3.5 与既有概念的区别（避免重复建模）

| 概念 | 是什么 | 与假设的区别 |
| --- | --- | --- |
| `facts` | 已确认的结论 | 假设是**待验证**的猜想；结算后才有 fact |
| `sub_goals`（阶段） | 进度里程碑 | 阶段回答"走到哪"，假设回答"还信什么" |
| `hints`（线索） | 人工给的方向 | 线索是外部输入，假设是系统内部待验证命题 |
| `intents`（行动） | 要做的一步 | 行动**服务于**假设（`hypothesis_id` 挂载） |

### 3.6 兜底

- 人工可删改假设（与阶段同样的兜底），避免"假设刷屏"；
- `refuted` 必须留 `note`（试过什么）——否定的结论同样是有价值的积累，将来同类目标可直接复用。

## 4. ❌ 明确不做（评测式机制，会带偏工具）

| 不做 | 理由 |
| --- | --- |
| 按产出/得分**强制排序** | 真实场景目标不能换；价值是深不是广。排序最多作为**建议**呈现 |
| **自动回收 / 自动止损** | 把研究员判断交给算术规则，可能在正要突破时掐断；与 ADR-0011 冲突 |
| 硬编码并发上限 | 评测平台规则；真实约束是授权时间窗、API 成本、并发限速 |
| "广度优先先拿简单的" | 真实渗透漏掉关键面等于失败，不是效率问题 |

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 环境基线空转（worker 不写） | 空基线时提示词**给出创建方法**；测试固定该行为 |
| 假设刷屏 | 人工可删改；假设必须可证伪（提示词约束 + 结算必须留证据） |
| 可交付性判定过严，把有价值的结论标成"证据不足" | 判定只做**标注**不阻断；`notes` 给的是"怎么补"而不是"不合格" |
| 这些机制在评测场景验证不出价值 | 下一步用**真实授权项目**验证（评测测不到报告质量、积累复用、人工协作） |
| 与既有机制冲突 | 新表与新字段全部可空/默认关闭；未使用基线与假设的项目行为不变 |

## 6. 与"观察者 agent"的关系

需求（有东西指挥全局）是成立的，实现方式刻意不新增 LLM 角色：

| 观察者职责 | 承担者 |
| --- | --- |
| 算术类：槽位占用、投入产出、停滞标记、候选排序 | **确定性代码**（可测、可解释、可复现） |
| 判断题：这条路还有没有希望、要不要换向 | **reason**（既有角色）+ 新输入（基线 / 假设 / 证据完备度） |

理由见 ADR-0015：职责重叠、"多一跳 LLM"的延迟与成本、与 ADR-0003「agent 不直接通信」冲突。
