# Sharp 使用文档

> 面向使用者。涵盖安装、配置、日常使用、各功能模块操作指南。
>
> 技术架构详见 `docs/ARCHITECTURE.md`，变更记录详见 `docs/CHANGELOG.md`。

---

## 1. 系统简介

Sharp 是一个**自动化渗透测试 / 安全评估**系统。核心思想：

1. 你创建一个**项目**，填写目标地址和测试目标
2. AI Worker（Claude Code / Codex 等）在 Docker 隔离容器内自动执行安全测试
3. 测试过程以**证据—行动图** 组织：每个发现是一个 Fact，每条探索路径是一个 Intent
4. 你可以在前端实时查看探索进度、证据图、时间线，也可以通过 AI 对话交互式分析

**适用场景**：Web 渗透测试、漏洞挖掘、CTF 解题、漏洞复测、业务逻辑测试、Android APK 安全分析、微信小程序安全分析。

## 2. 环境要求

| 依赖 | 最低版本 | 说明 |
|---|---|---|
| Python | 3.12+ | 运行启动器脚本 |
| uv | 最新版 | Python 包管理器（`pip install uv` 或 `curl -LsSf https://astral.sh/uv/install.sh \| sh`） |
| Docker | 最新版 | 运行 Worker 容器（需能执行 `docker run` / `docker exec`） |
| 操作系统 | macOS / Linux / Windows | 跨平台支持 |

运行 `./sharp doctor` 可自动检查环境是否就绪（含 DB 大小与可回收空间）。

服务已在运行时，也可以直接问它存储情况：

```bash
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/maintenance/storage
```

返回 DB/WAL 大小、**可回收空间**、逐表行数（降序，一眼看出哪张表在长）、聊天留存口径与上次整理时间。
留存口径是固定的：**每个会话最多留 200 条消息、每个聊天 store 最多留 50 个会话**（更老的连消息一起删），
数据库文件本身在启动时按门控整理（30 天一次，或可回收空间超过 100MB）。

## 3. 安装与配置

### 3.0 worker 镜像的架构选择（Apple Silicon）

`fetch_vendor.sh` 默认跟随本机架构（`uname -m`），也可显式指定：

```bash
cd container
ARCH=arm64 ./fetch_vendor.sh          # 只想看看会下载什么：PRINT_ONLY=1 ARCH=arm64 ./fetch_vendor.sh
docker build --platform linux/arm64 -t sharp-worker:latest .
```

- **arm64 原生构建**（Apple Silicon）省掉 qemu 模拟，容器内 nuclei/ffuf 这类 CPU 密集工具快数倍。
- **架构差异**：`naabu` 上游没有 linux/arm64 构建，arm64 镜像里不含它（Dockerfile 自动跳过，端口扫描可用 nmap 替代）；`ripgrep` 的 arm64 deb 也不存在，改走 Debian 仓库。
- **不要混架构**：`vendor/` 是平面目录，切换架构时脚本会用 `.arch` 标记拦住你（混用二进制会在容器里 `exec format error`）。真要切换：`FORCE=1 ARCH=<arch> ./fetch_vendor.sh`。

### 3.1 获取项目

```bash
# 如果是 git 仓库
git clone <repo-url> Sharp-v2
cd Sharp-v2
```

### 3.2 配置 AI 密钥

密钥配置有两种方式：

**方式一：secrets.env 文件（推荐）**

```bash
cp secrets.env.example datas/sharp/secrets.env   # 模板在仓库根目录
# 编辑 secrets.env，填入你的 API Token
```

**方式二：界面配置**

启动后在 Settings（设置）页面中配置：
1. 选择 Dispatcher 模式（Anthropic / OpenAI / Inflection）
2. 填入对应的 API Token、模型名、Base URL
3. 点击保存，然后重启 Dispatcher

### 3.3 dispatch.yaml 配置（高级）

`dispatch.yaml` 是调度器的主配置文件，关键配置项：

```yaml
runtime:
  interval: 3              # 调度循环间隔（秒）
  max_workers: 8           # 全局最大并发 Worker 数
  max_running_projects: 3  # 同时在跑的项目数
  max_project_workers: 4   # 单项目最大 Worker 数
  healthcheck_timeout: 60  # 健康检查超时（秒）

tasks:
  bootstrap:
    timeout: 400           # 初始探索超时（秒）
    conclude_timeout: 90   # 兜底总结超时（秒）
  reason:
    timeout: 300           # 推理超时（秒）
    max_intents: 4         # 每轮最多新增行动数
  explore:
    timeout: 300           # 探索超时（秒）
    conclude_timeout: 180  # 兜底总结超时（秒）：结论是唯一把一轮工作带回图里的通道，
                           # 太紧会在并发下被 timeout 杀掉、整轮白干（实测 90s 会命中）

workers:
  claude_worker:
    type: claudecode
    max_running: 3
    env:
      ANTHROPIC_MODEL: "${SHARP_MODEL:-sonnet}"                  # 版本无关的别名
      ANTHROPIC_BASE_URL: "${SHARP_BASE_URL:-https://api.anthropic.com}"
```

> **模型与端点请显式配置**：默认值是**官方端点 + `sonnet` 别名**，可用 `SHARP_MODEL` /
> `SHARP_BASE_URL` 覆盖（第三方网关、兼容端点都通过这两个变量接）。
> **不要**把某家第三方中转写进默认值——那会让所有用户（包括没有该网关账号的人）默认走别人的
> 流量通道，既是供应链风险也是上手障碍。同理，`ANTHROPIC_AUTH_TOKEN` 走 `SHARP_ANTHROPIC_AUTH_TOKEN`
> 环境变量注入，不写进配置文件。

### 3.4 首次启动

```bash
./sharp doctor    # 检查环境
./sharp           # 桌面窗口模式启动
```

首次启动会：
1. 自动 `uv sync` 安装 Python 依赖
2. 检查密钥配置
3. 确保 Worker Docker 镜像存在（缺失时按 `docker build ./container -t sharp-worker:latest` 本地构建）
4. 启动 API 服务器 + Dispatcher

## 4. 启动方式

| 命令 | 说明 |
|---|---|
| `./sharp` | 桌面窗口模式（默认，pywebview 打开独立窗口） |

**单实例保护**：同时只能运行一个 Sharp 实例。端口被占时会给出明确提示。

## 5. 初始化与认证

### 5.1 首次初始化

第一次访问时，系统会要求你**设置管理密码**：
1. 打开浏览器/桌面窗口，看到初始化页面
2. 阅读并同意免责声明
3. 设置密码（需含大小写字母+数字，至少 8 位）
4. 设置完成后进入登录页

### 5.2 登录

- 输入密码登录
- 登录令牌存储在浏览器 **sessionStorage**：刷新页面保持登录，**关闭标签页需重新登录**（P0 安全修复后不再长期保存明文；升级后首次打开会自动迁移旧令牌并清除旧值，你不会被登出）
- **重启服务端后需重新登录**（JWT 密钥每次启动重新生成）

### 5.3 修改密码

在 Settings（设置）页面可以修改密码。

## 6. 项目管理

### 6.1 创建项目

1. 在 Dashboard 或项目列表页，点击「新建项目」
2. 填写信息：
   - **标题**：项目名称
   - **Origin（起点）**：目标地址、授权范围等已知信息
   - **Goal（目标）**：要验证的漏洞类型、要获取的权限等
   - **资产类型**（2026-09-06）：Web 站点 / 小程序 / App 三选一——决定该项目在**资产中心**的归组。选 Web 时下方资产键（域名）会从 Origin **自动提取**（可手动改）；小程序/App 建议直接在对应分析器上传创建（自动带 AppID/包名），也可建空壳后从分析器追加
   - **Hints（提示）**：可选，给 AI 的额外提示（如测试账号）
   - **任务模式**（可选）：**渗透测试**（默认）或 **评分类任务**——决定产物语义，见下方说明
3. 可选择项目模板快速填充（见下）

> **任务模式**：`渗透测试` 是默认定位，界面与 AI 提示词里都不出现"分数/旗帜"这类概念；`评分类任务`（CTF / 授权评测靶场）才启用旗帜记分、记分板与 flag 输出规范。两者可在项目「操作 ⋯」菜单里随时切换，历史数据不会丢（评分类数据只在评分类模式下呈现）。

### 6.2 项目模板

内置 6 种模板：

| 模板 | 适用场景 |
|---|---|
| **攻防渗透测试** | 全流程渗透，目标是从普通用户到内网横移的权限链 |
| **漏洞挖掘** | 尽可能发现并验证安全漏洞，按优先级排序 |
| **CTF 题目** | 快速解题，20 分钟超时策略 |
| **漏洞复测验证** | 对已有漏洞逐一复测（已修复/未修复/部分修复） |
| **业务逻辑测试** | IDOR/越权/竞态/状态机等逻辑漏洞专项 |
| **自定义模板** | 可保存自己的模板到本地 localStorage |

### 6.3 项目状态

| 状态 | 图标 | 含义 |
|---|---|---|
| Active | 🔄 | 正在运行，Dispatcher 在调度 Worker |
| Stopped | ⏸ | 已暂停，不调度新任务 |
| Completed | ✅ | 已完成（有 Intent 指向 Goal） |

操作：
- **暂停/恢复**：项目列表中的开关按钮
- **重开已完成项目**：打开项目 → 操作菜单 → 重开（会删除完成记录，恢复探索）
- **重命名**：项目详情页 → 操作菜单 → 重命名
- **删除**：项目列表页 → 删除按钮（有确认弹窗）
- **收藏/标签**：星标收藏、添加自定义标签、按标签筛选

### 6.4 项目列表

- **搜索**：按标题、ID 搜索
- **筛选**：按状态（全部/进行中/已暂停/已完成）、收藏、标签筛选；资产中心 chip 过滤
- **布局（2026-09-06）**：**行式列表**——每条一行（状态点 + ID + 类型 + 标题），运行/风险信号与计数在第二行，**操作按钮悬停该行时出现**（星标/重命名/快照/AI 报告/暂停/删除）
- **批量操作**：停止所有进行中项目

### 6.5 资产中心（2026-09-06，批次 11.4）

同一目标（域名 / 小程序 AppID / App 包名）开的多个项目会自动聚成**一组资产**：

- 进入项目列表页，顶部点击 **「资产中心」** 展开组列表（每组显示：类型徽章 Web/小程序/App + 资产键 + 项目数 + ⚠高危漏洞合计）
- **点击某个资产 chip** → 下方项目列表只显示该资产下的项目（再次点击或「清除资产筛选」恢复全部）
- 无域名可提取的 Web 项目归入「未归类」

资产键的取法：Web 项目从起点 URL/域名自动提取主机名（新建时可手动指定 `target_kind` 与 `asset_ref`）；小程序分析用 AppID；App 分析用包名。同名资产键的项目共享这一聚合入口——"这家公司测到哪了"一眼可见。

> **2026-09-15 修正（两处，都与"真实 origin 是句子"有关）**：
> ① `asset_ref` 此前只认"以 `http(s)://` 开头的 URL 或裸域名"，而真实 origin 事实是**句子**
> （`目标地址：http://…` ＋ `授权范围：…`）→ 提取结果为空串 → 该项目的资产聚合与接口账本**静默失效**。
> 现在与知识库共用同一套主机规范化（`sharp/server/hostkey.py`），句子形式也能解析出主机。
> ② 裸 IP 此前被拒绝作为资产键，**但** `http://192.168.1.1:8099/` 这种写法却能通过 —— 两处口径自相矛盾。
> 现在统一接受 IP：授权项目里大量目标就是裸 IP，拒绝它等于让最需要资产台账的场景反而没有台账。
>
> 注意两者输出**语义不同**、不可互换：**资产键保留完整主机**（`sub.a.com` → "是哪台机器"），
> **知识键做根域归并**（`sub.a.com` → `domain:a.com` → "哪些目标能相互复用经验"）。


**接口账本（结构化资产记忆，2026-09-06）**：AI 每次结论（conclude）时，凡结论文本里出现的完整 API URL（如 `https://host/api/users`）会自动登记进该资产的接口账本（静态资源/首页等自动过滤）。之后**同资产开新项目**，项目启动提示里会自动注入一条「资产覆盖」提示：该资产此前发现过哪些接口、哪些还没验证、分别来自哪个旧项目——"上次发现的接口这次直接接着测"不再靠运气。资产中心的每个 chip 也显示「· 接口 N/M 待测」表示该资产的登记数与未验证数。

**目标空间详情（2026-09-09，P2-A）**：选中某个资产后，同一行会出现 **「空间详情」** 按钮，打开后可一次看清
**这个资产（而不只是某一个项目）打到哪了**：

| 板块 | 内容 |
|---|---|
| 概览 | 资产键、类型徽章、产品标注、项目数 / 证据 / 行动 / 结论、首轮时间 |
| **接口台账** | 跨项目共享的接口：**待验证**（黄色，接着测这些）/ 已验证 / 已排除，悬停看结论与来源项目 |
| **历史发现** | 跨项目的结论按严重度汇总、待确认的高危数、**证据不足的结论**（交付前需补齐，含缺什么、来自哪个项目） |
| 已沉淀知识 | 该目标键下的知识条数（凭据只计条数，值见知识库）、**已验证不通**清单（换同类目标时最省时间的一条） |
| 战线 | 该资产下的全部项目，点一下直接进项目 |

> 为什么值得单开一个视角：接口台账本来就是**按资产键跨项目共享**的 —— 此前点资产芯片只等于"过滤项目列表"，
> 看不到共享的那部分。"这家测到哪了、还差什么"要一次说清，就得看这个层面。

> **2026-09-09 补全（P1-B）：台账不再只增不减。** 此前 `status` 只有"已发现"一种取值 ——
> 测过的接口永远挂在"未验证"里，覆盖报告的盲区清单因此越用越吵。现在：
> - **worker 每轮都看得到台账**（右栏提示词里注入：哪些已发现待评估、哪些已验证、哪些已排除），优先推进未评估的，不重复测已完成的；
> - **worker 把评估写回**（`verified` 测过了 / `dismissed` 确认无价值），台账状态随之推进，盲区收敛；
> - 台账里没有、但 worker 确实测过的接口会被**新建**并记为已评估 —— 只认完整 URL 的自动登记（刻意保守）漏掉的纯路径结论，靠这条补上。

> **2026-09-09 补全（P2-D）：任何写入证据的入口都会沉淀。** 此前只有"行动结论"这一条路径
> 会登记接口台账（知识提取更是只由 dispatcher 触发），于是从**对话里"写入证据图"**、
> **重开项目的外部反馈**、**Android / 小程序分析事实**写进图里的内容**什么都不产出** ——
> 同一条证据，走哪个入口决定了它有没有沉淀价值。
> 现在这些入口统一走同一套副作用（登记接口台账 + 抽取跨项目知识）：你在对话里确认的一个接口，
> 下一个打同类目标的项目就能直接看到。

## 7. 证据—行动图

### 7.1 什么是证据图

项目的探索过程以**有向图**组织：

```
Origin（起点）──→ Fact f001 ──→ Intent i001 ──→ Fact f002 ──→ Goal（目标）
      │                                    │
      └──→ Hint（提示）                     └──→ Intent i002 ──→ ...
```

- **起点（Origin）**：你填的目标地址与已知信息
- **验收标准（Goal）**：你要验证的漏洞 / 要拿到的东西
- **证据（Fact）**：已确认的发现（AI 产出，带来源行动）
- **行动（Intent）**：待执行的一步探索（规划器派生、bootstrap 自动建或人工添加）
- **线索（Hint）**：你补充给 AI 的方向信息

> 以上是界面与文档的对外叫法；数据表内部仍叫 `facts` / `intents` / `hints`（映射见 `docs/GLOSSARY.md`）。

### 7.2 图操作

- **拖拽**：拖动节点重新布局
- **点击节点**：选中并查看详情（右侧面板）
- **多选 Fact**：Ctrl+点击多个 Fact，可批量创建 Intent
- **布局切换**：4 种布局引擎（dagre 竖向 / dagre 横向 / klay / elk）
- **缩放**：滚轮缩放，双击适应屏幕
- **血缘高亮**：选中 Fact/Intent 时高亮其来源链路

### 7.3 侧边面板

| Tab | 内容 |
|---|---|
| 详情 | 选中证据/行动的详细信息（ID/描述/来源/时间），含行动的操作按钮（认领/心跳/释放/结论） |
| 线索 | 项目所有人工线索（Hint），可增删 |
| 日志 | 时间线视图：项目事件流（见下） |
| 规划 | **阶段目标 + 未验证假设**（两段同一面板）：<br>· **阶段目标**：AI 规划器自动提出的推进阶段或你手动添加；可标开始/完成/放弃，顶部显示 done/total 进度<br>· **未验证假设**：AI 或人工提出的可证伪命题，可标「开始验证 / 成立 / 不成立」（成立需指向证据，不成立需写清尝试） |
| 实时 | worker 的实时输出（运行中任务） |

面板宽度可拖拽调整（拖左侧分隔条）。

> **标签上的计数只在非空时显示**：`线索 / 规划` 会带上条目数（`规划` = 未结算假设 + 未完成阶段），数量为 0 时隐藏。
> 这不只是审美 —— 标签行有 6 个标签平分面板宽度（默认 320px），多一个 `0` 就会让该标签折成两行、
> 看上去与邻居不一致。约定见 ARCHITECTURE §9.4 规范 4。

> **线索是你中途纠偏的唯一通道（2026-09-16 修复）**：线索会被**每一轮规划**重新读进提示词，
> 所以项目跑起来之后随时可以补一条（例如"b-01 这条死胡同别再打了，改打内网跳板"），
> 规划器当轮就能看到并按它调整方向。
> 此前线索只在**建项那一刻**注入一次，运行中补的线索不会被任何 agent 读到（详见 CHANGELOG
> 2026-09-16「人工线索只写不读」）。
> 提示词里也写明了效力等级：**线索与图里已有结论冲突时以线索为准** —— 你掌握 AI 看不到的信息；
> 但线索只是方向、不是证据，AI 仍需落到证据才能写结论。
> 相关：项目连续 3 轮规划都没有新证据会被判「停滞」并**暂停规划**，此时补一条线索即可解除停滞并把方向重新给出去。

### 7.4 证据人工纠错与完成前盘点（2026-09-06，批次 11）

**证据纠错**：点击图中任意非 origin 的证据节点 → 右侧详情「人工校验」区 → 「修正 / 标注」：

- **标注不可信**：勾选「标注为不可信」保存——保留原文但该证据不再作为结论依据；图中节点呈 ⚠ 琥珀虚线警示，AI 阶段上下文会提示不要基于它推进

## 8. 行动（Intent）与心跳

### 8.1 行动生命周期

```
创建 → 认领（Claim）→ Worker 执行 → 心跳续约 → 结论写入（Conclude）→ 完成
                              ↓
                         释放（Release）→ 其他 Worker 可认领
```

### 8.2 操作

> **规划器职权（2026-09-09）**：AI 的规划环节（reason）现在可以**放弃死路步骤**（行动标为「已放弃」，图上留痕但不再派工）和**调整步骤优先级**（数字越大越先执行）——你在行动详情能看到这两项状态。多目标/有时限任务里，这能避免低价值步骤长期占用 worker。
>
> **项目截止时间**：项目工作台「操作 ⋯」→「设置截止时间」（ISO-8601 UTC，如 `2026-09-10T09:00:00Z`，留空清除）。到期后调度器**不再派发新任务**（运行中的自然结束），并提示 AI 收敛已有结论——适合跑分/限时交付场景。

- **创建行动**：选中若干 Fact → 「创建行动」→ 填写描述 → 可选择同时认领
- **认领**：未认领的行动可被认领（发送心跳即自动认领）
- **心跳**：已认领的行动需定期发送心跳（超时阈值由 `intent_timeout` 配置，默认 5 分钟）
- **释放**：放弃当前行动，其他 Worker 可接手
- **结论**：为行动写入结论（成为新的 Fact）
- **完成项目**：当一个 Intent 的结论指向 Goal 时，项目完成。**完成说明必须是有含义的一句话**（至少 4 个字符，且不能是纯数字/纯符号）——它是事后复核"这个项目凭什么算完成"的唯一依据，写成 `1` 之类会被拒绝（422）

### 8.3 心跳进度条

行动面板中心跳进度条实时显示：
- 绿色：心跳新鲜
- 黄色：心跳即将超时
- 红色：心跳已超时（Intent 标记为 stale）

### 8.4 高危行动与人工审批（Approval Gate）

高危/严重风险的行动在**执行前**会被挂起，等待人工批准/拒绝（AI 无法自行放行或自批）。审批粒度 = 行动。

#### 风险等级

AI 探索中产生的每个行动都会被服务端按风险等级分类（模型标注仅供参考，服务端关键词判定为准，取两者更高等级）：

| 等级 | 含义 | 示例 | 默认是否拦截 |
|------|------|------|:---:|
| **low** | 信息收集/被动/只读 | 端口扫描、枚举、DNS、抓包 | 否 |
| **medium** | 主动探测但不改数据 | SQL 注入查询、XSS 探测、参数篡改 | 否 |
| **high** | 可能改变系统状态 | 文件上传、SQL 写操作、命令执行测试 | **是** |
| **critical** | 攻击性/破坏性 | webshell 上传、提权、删库、DoS | **是** |

拦截策略在服务端通过环境变量控制（**不依赖** `dispatch.yaml`——该文件 worker 端可改，不作为安全边界）：

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `SHARP_APPROVAL_ENABLED` | `true` | 审批闸门总开关；设为 `false` 时高危行动不被门禁（仅测试/明确单操作者流程用，不会静默自批） |
| `SHARP_APPROVAL_BLOCK_MEDIUM` | `false` | medium 是否也拦截 |
| `SHARP_APPROVAL_TIMEOUT_HOURS` | `24` | 待审批超时小时数（下限 1） |

#### 审批流程

1. 侧边栏点击「审批」（带红色角标显示待审批数）进入**审批中心**；
2. 列表展示待审批行动：风险标签（low=灰/medium=黄/high=橙/critical=红）、行动描述、来源 Fact、提交时间、**超时倒计时**（默认 24h，超时自动置为"已过期"=不执行）；
3. 点击详情可查看完整描述、风险原因、项目背景与审批历史；
4. **批准**：一键放行（可填备注），dispatcher 下一轮调度自动执行该行动；
5. **拒绝**：必填理由，理由会自动写成一条 Hint 回喂给 reason，防止 AI 重复提出同类高危行动。

> 已过期（expired）的行动**永远不会被自动放行**，如需执行需重新创建行动。

#### 项目内的待审批行动

- 项目摘要顶部显示「N 个高危行动待审批」提示条；
- 图中行动节点若为待审批状态，以**红色虚线圆 + 「审」字**标记，点击可弹出审批卡快速处理。

#### 紧急模式

特殊场景下（如已获授权、时间紧迫）可临时开启某项目的紧急模式，期间该项目 high/critical 行动自动放行（**严格按项目生效**，只影响你开启的那一个，其它项目照常走审批）：

- 入口有两个：**项目工作台「操作 ⋯」菜单**（自动选中当前项目，最顺手）或 **审批中心「+ 开启紧急模式」**（弹窗下拉任选项目）；**必须填写原因 + 预计时长**；
- 项目菜单里的该项会实时显示状态：未开=「开启紧急模式（高危自动放行）」；已开=琥珀高亮「关闭紧急模式（恢复人工审批）」，点击即关；
- 开启后项目顶部显示醒目的红色横幅（含原因）；
- 到预设时长自动关闭，也可提前手动关闭；
- 所有开关动作都会写入审批事件审计记录（`approval_events`）。

#### 报告导出二次确认（兜底）

当报告被判定为高危（`high_risk=true`）时，导出操作会先返回 `pending_confirm` 状态并弹出确认框，**二次确认后才真正生成报告文件**，防止高危结果在无意识下被导出。

### 8.4.1 急模式下的复核（审批中心「急模式放行」）

开启紧急模式后，**高危行动不再进入待审批**（创建即自动放行），所以人工的介入点从"审批"变成了"**复核**"：

- 审批中心新增「**急模式放行**」tab：列出所有被自动放行的高危动作（含项目、风险等级、执行状态、是否已产出证据），未复核的会标出
- 每条可做**事后复核**：「确认无碍」或「需跟进」（标记"需跟进"必须写明跟进事项）
- 顶部会提示还有多少条未复核；复核记录与开关动作一并写入审计轨迹
- **含义**：急模式省掉的是"当场拦一下"，不是"留痕"——放行动作与复核结论都可追溯，事后能说清"那段时间自动放行了什么、谁看过、结论是什么"

> 注：AI 不能复核自己放行的动作（该类端点仅限登录用户），这与审批端点同一条安全边界。

### 8.5 漏洞库（Vulnerability Library）

> **产物类型与记分（2026-09-09）**：漏洞库现在按**产物类型**分流——「漏洞」（默认，安全发现）与「旗帜 / 其他产物」（评分类任务的产出，如 CTF/跑分的 flag，可带分值）。筛选器可切「全部类型 / 漏洞 / 旗帜 / 其他产物」；评分类项目在漏洞库顶部显示**记分条**（已获得 N 个旗帜 / 得分合计 M）。AI 在评分类目标下会把每个 flag 以 `kind:"flag"` + 分值入账，渗透目标则照旧记漏洞。

Sharp-v2 在探索过程中会自动提取结构化漏洞记录，独立于 facts/intents 管理。

#### 自动漏洞提取

AI worker 在 explore 阶段确认漏洞后（通过布尔 oracle 协议验证），在 JSON 输出中附带 `findings` 数组。Dispatcher 解析后自动调用服务端 API 创建漏洞记录，关联到产出该漏洞的 fact。

每个漏洞记录包含：
- **标题** + **严重度**（critical/high/medium/low/info）
- **URL**（受影响的端点）
- **描述**（漏洞类型与原理）
- **证据**（curl 命令 + 响应观察）
- **复现步骤**（步骤化操作指南）
- **影响**（攻击者可达到的效果）
- **修复建议**

#### 轻量 Verifier

创建漏洞时自动判定初始状态：
- 有 `evidence` 或 `reproduction` → 自动标记为「已确认」（有 PoC 证据）
- 否则 → 标记为「待审」（需人工复核）

#### 漏洞库页面

侧边栏点击「漏洞」进入漏洞库视图：
- **严重度概览**：5 列统计卡（严重/高危/中危/低危/信息）
- **筛选器**：按严重度 + 状态筛选
- **列表**：每条漏洞显示严重度标签、状态标签、标题、URL、创建时间、描述摘要
- **详情弹窗**：点击漏洞可查看完整详情（描述/证据/复现/影响/修复建议），并执行操作：
  - **确认漏洞**：标记为 confirmed
  - **忽略**：标记为 dismissed（不在统计中计数）
  - **设为待审**：重新标记为 pending
  - **删除**：永久删除记录

#### Dashboard 统计

仪表盘新增「确认漏洞」统计卡片，显示总漏洞数和高危数量。

#### 大屏节点漏洞色

攻击链路图中，含有关联漏洞的 fact 节点会叠加漏洞色边框：
- 🔴 严重（critical）：3px 红色边框 + 红色光晕
- 🟠 高危（high）：2.5px 橙色边框
- 🟡 中危（medium）：2px 琥珀色边框
- 🔵 低危（low）：1.8px 蓝色边框
- ⚪ 信息（info）：1.6px 灰色边框

颜色取该 fact 关联漏洞中的最高严重度。已忽略（dismissed）的漏洞不计入。

### 8.6 任务预算与暂停调度（2026-08-29）

#### 任务预算

由于 API token 消耗无法直接获取，使用**任务次数**作为代理度量。每个项目可设任务预算，当调度器分发的任务总数达到预算时，停止派发新任务并写入一条提示 hint。

- **设置预算**：`PUT /projects/:id/budget`，`task_budget` 设为 0 表示无限制
- **查看用量**：项目摘要中 `task_count` / `task_budget` 字段；前端卡片上显示 `count/budget`（无限制时不显示）
- **预算耗尽**：调度器写入 hint「任务预算已耗尽（N/M）」，项目保持在 active 状态，可手动提高预算后继续

#### 暂停调度

项目暂停调度（`paused`）是一种轻量暂停——与 `status=stopped` 不同：

| | stopped | paused |
|---|---|---|
| 取消运行中任务 | ✅ 是 | ❌ 否（自然完成） |
| 释放 worker | ✅ 是 | ❌ 否 |
| 新 dispatch | ❌ 跳过 | ❌ 跳过 |
| 恢复方式 | `PUT /status` → active | `PUT /paused` → false |

适用场景：不想中断当前正在跑的扫描，但暂时不想给这个项目派新任务。

- 项目卡片和详情页有「止调度/续调度」按钮
- 暂停时卡片显示紫色「调度暂停」徽章
- 详情页标题栏图标变为 ⏸

### 8.7 跨目标知识复用（2026-08-29；**2026-09-15 重做**）

Sharp-v2 在探索过程中自动积累 credential / endpoint / fingerprint / **dead_end** 知识，跨项目复用。

> **重做说明**：此前这条链路**一次都没真正生效过** —— 真实 origin 事实是句子
> （`目标地址：https://…\n授权范围：仅主域`），而旧解析器只认裸 URL，解析失败后注入函数直接跳过；
> 加上写入键被算成 `flag.txt`、`scan.py` 这类文件名。所以"知识库里有数据"并不等于"经验被用上了"。
> 现在键、读取路径、匹配维度都已修正，并修掉了库里 166 行历史脏键。

#### 匹配键：目标键 + 产品维度

知识按**规范主机键**归档，四种形态一眼可辨：

| 键 | 含义 |
|---|---|
| `domain:example.com` | 域名目标 |
| `ip:10.0.100.58` | IP 目标（渗透场景主力） |
| `host:internal-api` | 内网服务名 |
| `unattributed` | 归属不明的历史数据：保留可查，但**不会**参与匹配 |

匹配是**两级**的，界面上分开呈现，因为可信度不同：

1. **同目标**（键一致）—— 可信，可直接用；
2. **同产品**（键不同但产品标注一致）—— 只是线索，需用本目标的证据复核。

#### 自动提取

AI worker 写 fact 后，自动提取四类知识：**credential**（凭据）、**endpoint**（接口）、
**fingerprint**（技术栈指纹）、**dead_end**（"这条路已验证不通"）。
`dead_end` 是单独一类，注入时会明确写成"**不要重复尝试**，除非有新证据" ——
换个域名部署的同类产品上，这条情报往往比一条正向结论更省时间。

> **凭据抽取会挡掉合成值**（2026-09-16）：worker 常在结论里引用源码，源码里满是占位符。
> `PLACEHOLDER_FLAG1`、`dk_live_a1b2c3d4…`、`{{db_password}}`、`1panel_password` 这类
> **明确写着占位/模板变量**的值不再进库 —— 因为凭据知识注入时的语义是"已知凭据、可以直接用"，
> 一条假凭据会让 AI 拿它去跑一轮真实登录。反向的边界同样重要：看着可疑（如
> `internal_admin_token_2024`）但**没有占位特征**的值一律保留，那可能正是题目/系统故意埋的
> 硬编码密钥。带特殊字符的口令也不再被截断（此前 `password=Admin@123` 会存成 `password=Admin`）。

#### 自动注入（两条路径）

| 时机 | 机制 |
|---|---|
| **创建项目时** | 解析 origin → 匹配知识 → 注入为 hint（来源标记 `knowledge_base`），agent 一开工就看得到 |
| **每轮规划时** | dispatcher 拉取 `GET /projects/{id}/knowledge` 渲染 `{knowledge}` —— 让**项目进行中新积累**的知识也能被当前项目用上 |

> Origin 里没有可用主机（如 APK / 小程序项目指向本地路径）时，不注入也不会报错 —— 但此时**不会**
> 用垃圾键硬存知识："条目不挂错键"比"条数好看"重要。

#### 产品标注（跨产品复用的开关）

同名产品换个域名/IP 部署时，只有目标键的知识一条都过不来 —— 用**产品标注**打通：

```bash
# 标注（也可带上 force=true 覆盖已有标注）
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"product":"Peplink MANGA"}' http://127.0.0.1:8000/projects/proj_001/product

# 看当前项目能用到哪些知识（同目标 / 同产品分开列）
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/projects/proj_001/knowledge
```

- worker 识别出目标产品后会在结论里上报 `product`，由 dispatcher 代写（也可人工直接标）
- **已有非空标注不会被某一轮的猜测覆盖**（产品名决定匹配走向，随轮次漂移会让复用结果不稳），
  要改需显式带 `force=true`
- 未标注（空值）**不参与**跨产品匹配 —— 空值是"未标注"，不是"同一个产品"

#### 存量数据修复工具

历史脏键可用工具重算（**默认 dry-run，改真实数据前请先备份**）：

```bash
python3 tools/rekey_knowledge.py            # 预览：会改哪些键、来源分布、有多少撞车
python3 tools/rekey_knowledge.py --apply    # 实际写入
```

重算来源优先级：项目 origin 事实 > 行内容 > 标题 > `unattributed`。
**刻意不把旧键当来源** —— 用垃圾推导垃圾只会把 `database.host`、`lang.runtime` 这类占位符洗回库里。

### 8.8 MCP 工具配置（2026-08-29）

Sharp-v2 支持为 claude code agent 注入外部 MCP（Model Context Protocol）工具服务器，扩展 agent 的工具能力。

#### 配置方式

> **推荐：Web 界面配置**（v13 起）

打开 Sharp-v2 Web 界面 → 设置 → 「MCP 服务器」区块。在此处可以直接添加、编辑、删除 MCP 服务器条目，保存后自动写入 `dispatch.yaml` 的 `mcp_servers` 段，无需手动编辑配置文件：

- **名称**：唯一标识，仅字母/数字/下划线/点/短横线（≤64 字符）
- **传输方式**：`http` 或 `stdio`
- **URL**（http 型）：MCP server 地址，bridge 网络下用 `http://host.docker.internal:<port>/...`
- **命令**（stdio 型）：启动命令
- **Headers / Env**：请求头与环境变量（可选）
- **启用**：是否启用该 server（默认启用）
- **最大工具数**：工具数上限，超限的 server 被跳过（默认 100）

保存后需重启 Dispatcher 生效。

<details>
<summary>手动编辑 dispatch.yaml（传统方式）</summary>

```yaml
mcp_servers:
  - name: burp-scanner
    transport: http
    url: http://host.docker.internal:8081/sse
    enabled: true
    max_tools: 50

  - name: local-tools
    transport: stdio
    command: node /opt/mcp-server/index.js
    enabled: true
```

| 字段 | 说明 |
|------|------|
| `name` | MCP server 名称（唯一标识） |
| `transport` | 传输方式：`http` 或 `stdio` |
| `url` | HTTP 型 server 的 URL（bridge 网络下用 `http://host.docker.internal:<port>/...`） |
| `command` | stdio 型 server 的启动命令 |
| `headers` | HTTP 请求头（可选） |
| `env` | 环境变量（可选） |
| `enabled` | 是否启用（默认 true） |
| `max_tools` | 工具数上限，超限的 server 被跳过（防 context 溢出） |

</details>

#### 预检与故障隔离

claude code 启动时会对 MCP server 做同步握手。如果某个 server 不可达，claude 会挂起超过 60 秒。为避免此问题，Sharp-v2 在注入前**自行预检**：

1. 对每个 HTTP 型 MCP server，在 worker 容器内用 Node 脚本做 JSON-RPC probe（initialize + tools/list，10 秒超时）
2. 不可达的 server 被排除，不写入 MCP 配置
3. 工具数超过 `max_tools` 的 server 被跳过
4. 全部 server 不可达 → 不注入 MCP（agent 正常运行无 MCP 工具）
5. stdio 型 server 不预检，直接包含
6. **预检结果缓存**：探测结果在进程级缓存 5 分钟（`MCP_PREFLIGHT_CACHE_TTL`），同一 server 的重复探测直接复用上次结果，避免每次任务都 spawn node 进程

> 预检结果写入容器内 `/tmp/sharp-mcp.json`，通过 `--mcp-config` 和 `--strict-mcp-config` 标志注入 claude。

#### 注意事项

- MCP 注入**仅对 claudecode driver 生效**，codex / pi / mock driver 不注入
- 修改 `mcp_servers` 配置后需重启 Dispatcher 生效
- HTTP 型 server 如果跑在宿主机上，容器内需用 `host.docker.internal` 访问（Linux 部署已自动配置 `extra_hosts=host-gateway`，无需手动设置）

### 8.9 双账号越权测试（2026-08-29）

Sharp-v2 的探索 prompt 内置了四维差分测试框架，支持真正的双身份交叉访问测试。

#### 四维差分

| 维度 | 做法 | 前置条件 |
|------|------|----------|
| **单身份 IDOR** | 同一会话换资源 ID 访问 | 无 |
| **跨身份差分** | A 会话读 B 的资源 ↔ B 会话读 A 的资源 | 需要 TOKEN_A + TOKEN_B |
| **垂直越权** | 低权账号 vs 高权账号访问同一资源 | 两个不同权限级别的账号 |
| **匿名差分** | 去掉 Token 重试已认证端点 | 无 |

#### 双账号凭证

bootstrap 阶段会在 worker 容器内生成 `creds.env`，格式为双账号布局：

```env
TOKEN_A=<主账号 token>
USER_ID_A=<主账号用户 ID>
# 如果有第二账号：
TOKEN_B=<第二账号 token>
USER_ID_B=<第二账号用户 ID>
```

agent 在 bootstrap 阶段被引导注册第二个账号（或使用已知测试账号），为 explore 阶段的跨身份差分测试准备凭证。

#### 覆盖度门禁

reason 阶段的覆盖度检查要求：
- 仅做单账号 ID-swap **不满足**越权覆盖门禁
- 缺少双账号时，agent 必须先提出"获取第二身份"的 intent
- 必须完成双身份交叉测试才能通过越权覆盖度检查

#### 身份标注

每个访问控制类 finding 会标注：测试身份、差分对、对照响应差异，便于后续复核。

### 8.10 AI 行为机制：假设 / 环境基线 / 可交付性 / 成绩回填

> 这一节讲"AI 在项目里怎么思考和记账"，与目标类型无关。

**未验证假设（深度推进的抓手）**：Sharp 会把"猜想"与"结论"分开管理——猜想（假设）写成**可证伪的命题**（"若 X 则 Y"），验证后结算为成立或不成立。

- **为什么有用**：真实渗透是假设驱动的（发现一个现象 → 猜它意味着什么 → 验证 → 新的猜想）。假设成为一等对象后，AI 会**优先做那些能一次证实或证伪某个假设的验证**，而不是漫游式试探；一条线挖到哪、还信什么，都有迹可循。
- **AI 被硬性要求回流假设**：规划器每轮都必须把"本次行动结算了哪个假设"和"观察到的新猜想"写回（`REQUIRED`，不是可选项）。此前这条只写在规则散文里、输出模板里连字段都没有，实测结果是假设表一直为空——"机制在纸面上通过、在现场没被触发"
- **否定的结论同样保留**：假设被判"不成立"时必须写清试过什么——"这条路试过不通"对后续同类目标是可复用的积累。
- **在哪里看**：项目右栏「**假设**」tab。AI 提出的假设会实时出现；你也可以手动添加，并做结算——**标记「成立」需要指向支撑证据（fact id），标记「不成立」需要写清尝试过什么**（与 API 的强制校验一致，避免出现没有依据的"确认"或"放弃"）。默认只显示未结算的，可一键切换看全部；误报的假设可直接删除（兜底防"假设刷屏"）。同一份数据也可用 API 读取：`GET /projects/{id}/hypotheses?only_open=true`。

**环境基线（作业前提，跨会话复用）**：Sharp 会把"已确认的环境事实"单独存成**环境基线**，与探索结论分开记账——网络连通性、平台凭据有效性、目标可达性、容器内工具可用性这类**前提**，确认一次后，后续每个行动都会直接读到，不再重复探测（此前同一件事会被反复验证，浪费授权时间）。

- **worker 如何维护它**：worker **不直连** Sharp API（容器里没有凭据，提示词也只教它测目标）。它在结论里**上报** `env_facts`（`[{"key":"network.vpn","value":"ok","note":"..."}]` 或 `{"key":"value"}` 都认，一次最多 20 条），dispatcher 收到后代为写入基线——与漏洞/结论的既有通道一致。人工也可通过 API 读写：`GET|PUT /projects/{id}/baseline`、`DELETE /projects/{id}/baseline/{key}`
- 环境事实是"前提"不是"结论"，因此**不会混进证据链与报告**——报告里只出现测试结果，不出现"VPN 已连通"这类背景噪音

**证据不足提示（可交付性）**：漏洞库会标出「⚠ 证据不足」的结论——它缺少可复现四件套中的某些项（原始请求/响应、复现步骤、影响说明、定位）。这类结论在生成的报告里会被写成「⚠️ 证据不足（缺 X）待补充」并归入待补充类，**不会被当成已确认漏洞**。补齐证据后标注自动消失（判定是实时计算的，不需要手动刷新状态）。漏洞库顶部会汇总"当前有多少条结论还不能对外提交"。

**历史任务的成绩回填（旗帜/记分）**——仅对**评分类任务**（`task_mode = scored`）有意义：早期评测项目在旗帜记分功能上线前就完成了，成绩只写在结论文字里，于是记分板显示 0 分。用回填工具从证据链里提取并补登：

```bash
python3 tools/backfill_flags.py --project proj_004          # 预览（默认 dry-run，不写库）
python3 tools/backfill_flags.py --project proj_004 --apply  # 实际写入
```

按 flag 值幂等（重复执行不会重复登记），题号与分值按证据文本就近匹配，取不到分值就记 0——**宁可缺分也不猜分**。

### 13.4 覆盖报告（2026-09-09，P1-A）

结项时最先被问的两件事：**打到了什么**、**哪块面根本没碰过**。覆盖报告把这两件事一次讲清：

| 入口 | 位置 |
|---|---|
| 工具栏「**覆盖**」按钮 | 项目详情右上角操作区，随时可看（结项后也在） |
| 结项弹窗里的「覆盖摘要」 | 点「完成」时与"未决事项"并排显示 —— 一个答"还有什么没了结"，一个答"覆盖到哪、哪里没碰过" |

报告分四节，顺序就是交付沟通里被问的顺序：

1. **打到了什么** —— 结论数与严重度、其中**证据不足**几条、接口台账（登记/已验证/从未验证/已排除）、沉淀下来的知识条数
2. **已验证不通** —— 死胡同清单（"这里试过了，不通"）。换个同类目标时，这一节最省时间
3. **盲区** —— 已发现却**从未验证**的接口、计划过但放弃的行动（含放弃原因）、未结算假设、未完成阶段、被标注不可信的结论等
4. **成本** —— 任务数/预算、证据条数、活动区间

命令行/脚本里取同一份数据（返回结构化字段 + 渲染好的 `markdown`）：

```bash
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/projects/proj_001/coverage
```

> **盲区只列"有据可查"的缺口**，并且**本报告不构成完整覆盖声明**。原因很实在：授权范围写在
> Origin/Goal 的自然语言里，没有机器可读的清单 —— 因此"未列出的面"不等于"已覆盖"。
> 我们宁可让你看到"这里有一处没验过"，也不给一份看起来完整、实则没依据的覆盖面清单。
>
> 另外：**凭据只显示条数、不显示值**（知识库里 credential 的标题就是凭据本身，写进报告等于到处散密钥）。
> 报告里的时间是"首次活动 → 最后活动"，不是结项时刻 —— 证据表本身没有时间戳，我们不编一个看起来精确的时间。

## 16. 常见问题

### Q: 操作一直转圈，或者提示"请求超时"？

前端请求有超时保护：普通操作 **30 秒**超时；AI 报告生成、小程序/APK 分析、深度分析派发、调度器重启等长任务放宽到 **10 分钟**。

超时只代表**浏览器不再等待**——服务端可能仍在处理。正确做法是稍后刷新页面看结果，**不要反复点击重试**（可能重复触发）。实时输出、AI 对话、动态分析是长连接流，不受此限制。

### Q: 为什么每次重新打开都要确认授权条款？

授权确认按**会话**记忆：同一标签页内刷新不会重复弹窗，但关闭标签页/浏览器后重新打开会再次要求确认。这是有意的——Sharp 会对目标发起**真实的安全测试请求**，确认动作属于使用边界的一部分，不该"同意一次终身免打扰"。弹窗不响应 ESC、点击遮罩也不会关闭，必须点「我已知悉并同意」。

### Q: 关闭标签页后要重新登录？

P0 安全修复后，登录令牌从 `localStorage`（长期明文保存）改为 **sessionStorage**：刷新页面保持登录、关闭标签页失效。这是有意为之——Sharp 是安全工具，令牌明文长期驻留浏览器意味着任何 XSS 都能永久接管。升级后首次打开会自动迁移旧令牌并清除旧值，你不会被登出。

### Q: 项目一直在 "初始态" 不推进？

AI Worker 可能在执行阶段跑重型扫描（nuclei 全模板等），撞满 bootstrap 超时被杀。解决方式：
- 在 Goal 中约束扫描强度（优先轻量侦察）
- 调大 `dispatch.yaml` 中 bootstrap 的 timeout

### Q: Worker 容器启动失败？

1. 运行 `./sharp doctor` 检查 Docker 环境
2. 确认 Worker 镜像存在：`docker images | grep sharp-worker`
3. 手动构建：`docker build ./container -t sharp-worker:latest`

### Q: 忘记密码怎么办？

删除数据目录中的 `sharp.db`（或其中的 auth 表），重启服务即可重新初始化：
```bash
rm ~/.local/share/sharp/sharp.db
```
> 注意：这会删除所有项目数据。

### Q: 修改了 dispatch.yaml 后如何生效？

重启 Dispatcher：设置页面 → Dispatcher 状态 → 重启 Dispatcher。或直接重启整个服务。

### Q: 如何查看 Worker 的实时输出？

项目详情页的「实时输出」面板会显示 Worker 执行过程中的 stdout（每 3 秒更新）。注意：`claude -p` 无头模式执行中基本静默，中间输出有限。

### Q: 多人能否同时使用？

可以。Sharp 支持多用户同时访问前端。但 Dispatcher 是单实例单线程的，所有项目共享一个调度队列。通过操作者名称区分不同用户。

## 17. 数据存储位置

| 数据 | 位置 |
|---|---|
| SQLite 数据库 | `~/.local/share/sharp/sharp.db`（或 `datas/sharp/` 目录） |
| 上传的 APK 文件 | `~/.local/share/sharp/uploads/app/` |
| 报告输出 | `./reports/` 目录 |
| Secrets | `datas/sharp/secrets.env` |
| 调度器配置 | `dispatch.yaml` |

### Q: SSE 断开后实时更新会停吗？

不会。SSE 连接异常断开时，系统会自动清除 SSE 状态并降级回轮询模式（每 5 秒全量刷新），同时尝试指数退避自动重连（最多 3 次：1s→2s→4s）。重连成功后恢复 SSE 实时推送。在此期间项目数据仍通过轮询保持更新。

### Q: AI 对话中途断开，之前的内容会丢失吗？

不会。如果因网络中断或关闭页面导致 AI 流式回复中途断开，系统会自动保存已生成的部分回复到对话历史中。重新进入会话时可以看到之前已收到的内容，不会丢失。

### Q: 登出后再登录，浏览器会变卡吗？

不会。登出时系统会自动清理所有事件监听器、定时器和 SSE 连接（`destroy()`），防止内存泄漏。重新登录后以干净状态重新初始化。

### Q: 浏览器 localStorage 数据损坏会导致白屏吗？

不会。本地存储（自定义模板、星标项目、项目标签）的读取均有异常兜底，JSON 解析失败时会回退到默认值，不会导致页面崩溃。

### Q: 高危行动一直卡在待审批，项目不推进怎么办？

这是**预期行为**。待审批（pending）的行动不会被调度执行，需要人工到「审批中心」批准或拒绝。若不想继续，可点「拒绝」并填理由（会自动回喂给 reason 避免重复提出），或直接忽略等它超时（默认 24h）自动置为过期。

### Q: AI 能自己批准自己的高危操作吗？

**不能**。审批与紧急模式接口只认登录用户的 JWT，Dispatcher 的内部 token 会被显式拒绝，AI 无法自批或自行绕过审批。

### Q: 模型标了 low 但描述里带"删除/提权"等危险词？

服务端会做关键词硬校验并**取更高等级**（最终等级 = max(模型标注, 服务端判定)），即使模型误判也会被拦截。模型标注仅供参考，不作为安全边界。

### Q: 紧急模式开启后是不是所有高危操作都会自动放行？

紧急模式期间该项目的 high/critical 行动会**自动放行**（不再等待审批）。但所有动作都会记入 `approval_events` 审计表，且需填写原因 + 预计时长，到期自动关闭，UI 有醒目红色警告。请仅在已获授权时使用。

### Q: Worker 会不会被目标 WAF 封 IP？

AI Worker 的 prompt 中内置了请求限速准则：同一主机请求间隔 ≥0.5 秒，遇到 403/429 自动冷却 5 秒，连续两次 403/429 会切换攻击面。扫描器要求低线程数（`-t 2` 或 `-t 4`）。但这是 prompt 层"软约束"，模型通常遵守但非 100% 强制。如目标 WAF 极其敏感，建议在 `dispatch.yaml` 中减少 `max_project_workers` 以降低并发压力。

### Q: AI 报告的漏洞都是确认的吗？

AI 在探索 prompt 中被要求遵循**布尔 oracle 确认协议**：报告漏洞前必须通过三条件差分判定（对照组基线、可复现性、竞争假设排除）。未通过全部条件的只能标记为"Possible"或"Unconfirmed"证据，不能作为确认漏洞。但这同样是 prompt 层约束，关键漏洞建议人工复核 PoC。
